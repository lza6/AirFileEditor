01上下文：这些变更为什么发生

项目原本有两套各自独立的文件复制引擎（旧 IoOptimizer 与新 HighPerformanceIoEngine）， Native 模式编排器仍走旧路径，进度看门狗、路径校验、shell 转义在三个 Orchestrator 里重复粘贴了约 60%。 同时，替换历史的数据流（getReplaceHistory()）早已存在，却在 UI 层没有任何入口——数据在，门关了。

直觉：与其再造第三套引擎，不如把两套合一、把重复抽基类、把已有数据流接到一个真实界面上。每一处都只做「融合」，不新造轮子。

06变更测验 · 你必须通过

点击选项查看对错与解析。

V14 的「引擎融合」把哪两套复制引擎合并成了 IoEngine？
✅ 正确。IoOptimizer（旧，375 行）与 HighPerformanceIoEngine（新，123 行）合并为统一 IoEngine，三种策略按文件大小自动切换。
IoEngine 对「极小文件（<32KB）」使用哪种复制策略？
✅ 正确。极小文件走直接缓冲区复制，避免 mmap 的页表开销；≥16MB 才走 mmap（Semaphore(16) 限流）。
替换历史 UI 的数据从哪一层流入 HistoryViewModel？
✅ 正确。HistoryViewModel 收集 ReplaceHistoryManager.history Flow，删除/清空直接写 DataStore 持久化，UI 状态随流更新。
独立审查发现的 P0 中，哪项是「测试与实现契约错位」？
✅ 正确。IoEngine 在 mmap 失败时会降级到自适应流（不抛异常），原测试却在 catch 里断言不得抛异常——一条永远不执行的死断言，无法证明真正走了 mmap 路径。已重命名并改为「mmap 或降级均完整复制」。
这轮变更最终推到了哪个 tag（push 到 GitHub）？
✅ 正确。main 已推送，最新 tag v14.1.1（含 v14.0.0 / v14.1.0 全部历史）。
