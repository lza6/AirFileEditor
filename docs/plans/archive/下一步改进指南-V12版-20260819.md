## 3. V12→V13 收口层：安全与任务闭环

### 3.1 任务状态机统一

#### 3.1.1 当前状态

`TaskPhase` 已定义 7 个状态，但 `ReplaceProgressManager` 使用字符串 phase，`isReplacing` 计算属性与 `TaskPhase` 枚举不统一。

#### 3.1.2 目标状态

**将所有 phase 统一为 `TaskPhase` 枚举，消除字符串 phase 和 `isReplacing` 计算属性的歧义。**

```kotlin
// 最终状态转移表
// IDLE → PREPARING → REPLACING → VERIFYING → COMPLETED
//              ↓            ↓           ↓
//              └──── FAILURE / CANCELLED ←┘
```

| 状态 | 进入方式 | 允许动作 | 可取消 | 可重试 | 可关闭 |
|------|----------|----------|--------|--------|--------|
| IDLE | 初始/重置 | StartReplace | 否 | 否 | 不显示 |
| PREPARING | 任务入队 | CancelReplace | 是 | 否 | 不显示 |
| REPLACING | 复制中 | CancelReplace | 是 | 否 | 可显示 |
| VERIFYING | 验证中 | CancelReplace | 是 | 否 | 可显示 |
| COMPLETED | 全部通过 | DismissTaskResult | 否 | 否 | 可关闭 |
| FAILURE | 任一失败 | RetryReplace / DismissTaskResult | 否 | 是 | 可关闭 |
| CANCELLED | 用户取消 | RetryReplace / DismissTaskResult | 否 | 是 | 可关闭 |

#### 3.1.3 具体修改点

**ReplaceProgressManager.kt：**
- `ProgressState.phase: String` → `TaskPhase` 枚举
- `isReplacing` 计算属性直接基于 `TaskPhase`
- `startMeasure()` 设置 `PREPARING`
- `finish()` 设置 `COMPLETED`
- `fail(message)` 设置 `FAILURE` + `errorMessage`
- `cancel()` 设置 `CANCELLED`，保留进度计数

**ConfigRepository.kt / ConfigRepositoryImpl.kt：**
- `getTaskProgress()` 返回的 `TaskProgress` 直接使用 `TaskPhase`
- `startReplace` 使用 `ExistingWorkPolicy.KEEP` 保证唯一任务
- `cancelReplace` 同时取消 WorkManager + 置为 CANCELLED
- `dismissReplaceResult` 只重置进度，不取消任务

**ReplacingViewModel.kt：**
- `CancelReplace` 成功后 phase 置 `CANCELLED` 而非 `IDLE`
- `DismissTaskResult` 将 phase 置 `IDLE`（关闭终态 Overlay）
- `RetryReplace` 复用上次 `lastReplaceIntent`
- 消除 `TaskPhase.valueOf(progress.phase.name)` 的反射转换

**ReplacingState.kt：**
- `isReplacing` 改为基于 `phase` 的计算属性

## 4. V13→V14 增强层：性能与体验革命

### 4.1 IO 性能引擎 2.0

#### 4.1.1 动态自适应缓冲区

**当前方案：** `IoOptimizer` 基于设备内存静态计算缓冲区大小（512KB-4MB）。

**改进方案：** 引入运行时反馈循环，根据实际 IO 延迟动态调整。

```kotlin
// 核心算法
class AdaptiveBufferManager(
    private val initialBufferSize: Int = 64 * 1024,  // 64KB 起点
    private val maxBufferSize: Int = 8 * 1024 * 1024, // 8MB 上限
    private val minBufferSize: Int = 4 * 1024,        // 4KB 下限
) {
    private var currentBuffer = initialBufferSize
    private val latencyHistory = FloatArray(10) // 滑动窗口

    fun adjustBuffer(latencyNs: Long): Int {
        // 将延迟记录加入滑动窗口
        System.arraycopy(latencyHistory, 0, latencyHistory, 1, latencyHistory.size - 1)
        latencyHistory[0] = latencyNs.toFloat()

        val avgLatency = latencyHistory.average()

        return when {
            // 延迟高 → 增大缓冲区减少系统调用
            avgLatency > 1_000_000 -> currentBuffer = (currentBuffer * 1.5).toInt().coerceAtMost(maxBufferSize)
            // 延迟低 → 减小缓冲区提高响应性
            avgLatency < 100_000 -> currentBuffer = (currentBuffer / 1.2).toInt().coerceAtLeast(minBufferSize)
            else -> currentBuffer // 保持当前
        }.also { currentBuffer = it }
    }
}
```

#### 4.1.2 mmap 零拷贝写入

**当前方案：** 使用 NIO `FileChannel.transferTo()` 进行零拷贝。

**改进方案：** 对大文件（>16MB）引入 mmap 内存映射写入。

```kotlin
// mmap 大文件写入实现
fun mmapCopy(source: FileChannel, target: RandomAccessFile, size: Long): Long {
    val mapped = target.channel.map(
        FileChannel.MapMode.READ_WRITE, 0, size
    )
    source.transferTo(0, size, mapped)
    mapped.force()  // 确保写回磁盘
    return size
}
```

**适用场景：**
- 文件 > 16MB → 使用 mmap 写入
- 文件 < 1KB → 使用小文件聚合策略
- 中等文件（1KB-16MB）→ 使用 NIO transferTo

#### 4.1.3 小文件聚合并批写入

**当前方案：** 每个文件独立复制，小文件时系统调用开销占比高。

**改进方案：** 将 <1KB 的小文件聚合成内存批次，统一 fsync 写入。

```kotlin
class SmallFileBatchWriter(
    private val batchSize: Int = 64, // 每批最多 64 个小文件
    private val flushThreshold: Long = 1024 * 1024 // 1MB 触发 flush
) {
    private val batch = mutableListOf<Pair<File, File>>()

    suspend fun write(source: File, target: File) {
        batch.add(source to target)
        if (batch.size >= batchSize || estimateBatchSize() >= flushThreshold) {
            flush()
        }
    }

    private fun flush() {
        // 批量读取源文件到内存缓冲区
        // 统一写入目标文件
        // 一次 fsync 同步所有
        batch.clear()
    }
}
```

#### 4.1.4 增量更新算法增强

**当前方案：** 全文件 MD5 比较。

**改进方案：** 引入抽样哈希 + 快速跳过策略。

```kotlin
// 抽样哈希：只比较文件头/尾/中间三段的哈希
// 80% 的文件变更发生在前 64KB 或后 64KB
fun samplingHash(file: File): String {
    val size = file.length()
    if (size < 1024 * 1024) return md5Full(file) // <1MB 全量

    val head = md5Region(file, 0, 64 * 1024)
    val tail = md5Region(file, size - 64 * 1024, 64 * 1024)
    val middle = md5Region(file, size / 2 - 32 * 1024, 64 * 1024)

    return md5(head + middle + tail) // 三段签名
}
```

#### 4.4.3 异常检测算法

```kotlin
class AnomalyDetector(
    private val windowSize: Int = 20
) {
    private val values = FloatArray(windowSize)
    private var index = 0

    fun detect(value: Float): AnomalyResult {
        values[index % windowSize] = value
        index++

        if (index < windowSize) return AnomalyResult.INSUFFICIENT_DATA

        val mean = values.average()
        val std = values.std()
        val zScore = (value - mean) / std.coerceAtLeast(1e-6)

        return when {
            zScore > 3.0 -> AnomalyResult.ANOMALY_HIGH // IO 异常升高
            zScore < -3.0 -> AnomalyResult.ANOMALY_LOW // IO 异常降低
            else -> AnomalyResult.NORMAL
        }
    }
}
```

### 8.4 动态并发控制参考

```kotlin
class AdaptiveConcurrencyController(
    private val minPermits: Int = 2,
    private val maxPermits: Int = 32,
) {
    private val ioLatencyMs = FloatArray(10)
    private var index = 0

    fun calculatePermits(): Int {
        val avgLatency = ioLatencyMs.average()
        return when {
            avgLatency < 5 -> maxPermits      // 极低延迟 → 最大并发
            avgLatency < 20 -> (maxPermits * 0.7).toInt() // 低延迟 → 中高并发
            avgLatency < 50 -> (maxPermits * 0.4).toInt() // 中等延迟 → 中并发
            avgLatency < 100 -> minPermits * 2  // 高延迟 → 低并发
            else -> minPermits                  // 极高延迟 → 保守
        }.coerceIn(minPermits, maxPermits)
    }

    fun recordLatency(ms: Float) {
        ioLatencyMs[index % ioLatencyMs.size] = ms
        index++
    }
}
```

## 10. 总结

### 10.1 核心原则

1. **安全优先**：所有改进以安全闭环为最高优先级
2. **渐进演进**：不推倒重来，在现有架构上持续优化
3. **测试驱动**：核心安全路径和状态机必须先用测试锁定
4. **体验至上**：每个功能改进都对应可感知的用户体验提升
5. **文档同步**：代码与文档必须保持一致性

### 10.2 成功标准

| 维度 | 当前状态 | V13 目标 | V14 目标 | V15 目标 |
|------|----------|----------|----------|----------|
| 测试覆盖率 | <50% | 70% | 80% | 90% |
| 构建时间 | ~5min | ~3min | ~2min | ~1min |
| IO 速度 | 基准 | +20% | +50% | +100% |
| 崩溃率 | 未知 | <0.1% | <0.05% | <0.01% |
| 用户满意度 | 未测量 | 基础反馈 | NPS > 30 | NPS > 50 |

### 10.3 给实施者的建议

1. **严格按阶段顺序执行**，不要跳阶段
2. **每个阶段完成必须通过对应测试门禁**
3. **安全相关的修改必须有两个以上开发者审查**
4. **每次发布前运行完整的回归测试套件**
5. **保持 CHANGELOG 与版本同步更新**
6. **旧产物清理在每个阶段完成后立即执行**
