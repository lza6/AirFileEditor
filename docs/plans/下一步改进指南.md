## 2. 执行摘要:当前唯一正确动作

### 2.1 一句话结论

**V13 收口已在工作树完成约 85%,当前最高优先级不是写任何新功能,而是:(1) 修复两个新发现的 P0 构建问题;(2) 跑通全量测试与质量门禁;(3) 把当前 71 文件的 V13 收口 diff 提交冻结,正式打 tag `v13.0.0`;(4) 然后才按本指南进入 V14。**

### 2.2 为什么必须先提交而不是继续改

1. **当前工作树是"V13 的全部价值所在"**:状态机统一、目标身份、解压安全、AIDL 白名单这些核心契约已经实现并有测试锁定,但它们只存在于未提交的 diff 里。任何一次误操作、一次 IDE 崩溃、一次其他 AI 的并发修改,都可能让这批修复丢失或被搅乱。
2. **后续所有 V14 工作都需要稳定基线**:V14 的性能引擎(mmap/小文件聚合/动态缓冲区)要改 IoOptimizer 和 Orchestrator,体验革命要改 UI 层——这些文件和 V13 diff 高度重叠。不先冻结 V13,就是"前面改 bug 后面加功能又出 bug"的经典陷阱。
3. **`project_specs.md` 已声称 V13 完成**(工作树中第 105-111 行标记"V13.0.0 已完成 ✅"),但 git 里没有对应提交——文档与版本库事实不一致,这是典型的"假收口"信号,必须消除。

### 2.3 推荐的 V14 主线

采用 **方案 B:性能与体验双引擎(V14.0.0)**——在 V13 冻结基线上,分四条增强主线,每条独立成版本里程碑:

- **主线一 · 性能引擎 2.0**:mmap 大文件、小文件聚合批写、动态自适应缓冲区、抽样哈希——全部要求"先基准、后优化、有回退"。
- **主线二 · 体验革命**:全量 Compose 迁移(消灭 12 个 XML 布局)、三层动画体系、无障碍闭环、触觉反馈。
- **主线三 · 事务与信任闭环**:备份恢复 UI 入口、OTA 结果契约化、审计日志结构化。
- **主线四 · 工程基建**:Gradle 配置缓存、CI/CD 门禁、构建提速、文档单一事实来源。

### 2.4 V14 不做什么(负面清单)

- ❌ 不推倒重写任何模块(V12 的四层拆分、V13 的安全契约全部保留)

## 4. 新发现的 P0 问题(旧指南未覆盖)

以下是本次(2026-08-22)实测代码后新发现的问题,**必须在 V13 提交前修复**,否则会污染基线:

### P0-A:`:data` 模块 compileSdk 与其他模块不一致 ⚠️ 构建隐患

- **证据**:`data/build.gradle.kts:8` 为 `compileSdk = 35`,而 `core/build.gradle.kts:8` 与 `app/build.gradle.kts:14` 均为 `compileSdk = 36`(`已验证`,逐文件核对)
- **危害**:三个模块 SDK 版本漂移。`:data` 依赖 `:core` 与 `:domain`,当 `:core` 使用了 SDK 36 的 API 而以 35 编译的 `:data` 消费时,可能出现运行时 `NoSuchMethodError` 或 lint 假阴性。AGP 8.x 也会对依赖 compileSdk 低于库 compileSdk 的情况给出警告。
- **修复方案**:`data/build.gradle.kts` 的 `compileSdk = 35` → `compileSdk = 36`,与全局对齐。一行改动,零风险。
- **验收**:`.\gradlew.bat assembleDebug` 无 compileSdk 警告,构建成功。
- **预估**:5 分钟。

### P0-B:Manifest 声明了不存在的 Service ⚠️ 死声明

- **证据**:`app/src/main/AndroidManifest.xml:53-55` 声明 `android:name=".service.FileReplaceService"`,但**全仓库 grep 无任何 `FileReplaceService` 类定义,也无任何 Kotlin 代码引用它**(实测 `Grep "FileReplaceService"` 在 app/core 源码零匹配,`已验证`)
- **危害**:该 Service 是早期版本的遗留声明(V1 曾用 Service 承载替换任务,V8 已迁移到 WorkManager)。Android 在声明了不存在的组件时通常不立即崩溃,但:(1) 占用 `FOREGROUND_SERVICE_SPECIAL_USE` 权限的解释义务;(2) 任何试图 `startService` 的旧代码路径会直接 `ClassNotFoundException` 崩溃;(3) 审核时增加无意义的解释成本。
- **修复方案**:
  - 方案 1(推荐):直接删除 Manifest 中该 `<service>` 声明,同时评估 `FOREGROUND_SERVICE`/`FOREGROUND_SERVICE_SPECIAL_USE` 权限与 `PROPERTY_SPECIAL_USE_FGS_SUBTYPE` 属性是否还有其他消费方(悬浮球?若悬浮球不依赖前台服务则一并清理);
  - 方案 2(保守):保留声明但实现空壳 Service——**不推荐**,违反"清理旧产物"原则。
- **验收**:删除后 `assembleDebug` 成功;冷启动、替换任务、悬浮球全路径手测无回归。
- **预估**:30 分钟(含权限影响面排查)。

### P0-C:README.md 版本号漂移 ⚠️ 文档与产品事实不一致

- **证据**:README 标题仍是 `v3.1.0`,而 `app/build.gradle.kts` 的 versionName 已是 `13.0.0`(`静态确认`)
- **危害**:用户按 README 找版本、报 issue 时对不上号;且 README 的"源码蓝图"章节描述的是单模块旧结构(`adapter/`、`service/` 等目录已不存在),会误导贡献者与其他 AI。
- **修复方案**:README 重写为 V13 事实(版本号 13.0.0、四模块结构、V13 能力清单),旧内容移入 `docs/` 或直接删除错误章节。**注意**:README 的营销性文案(产品介绍、Shizuku 教程)有保留价值,只改事实错误部分。

### 5.1 主线一:性能引擎 2.0(核心价值:快)

#### 5.1.1 现状盘点(`静态确认`)

`IoOptimizer`(333 行)已具备:对象池缓冲区复用(`acquireBuffer`/`releaseBuffer`,第 90-103 行)、`fastCopy` 主路径、`fastCopySmallFile` 小文件分流、`needsUpdate` MD5 增量比对、`parallelProcess` 并发框架。`AdaptivePermitScheduler` 已基于 CPU/内存/IO 动态调整并发度(V10)。

**短板**:缓冲区大小是启动时按设备内存静态计算(512KB-4MB),没有运行时反馈;大文件走 `transferTo` 未用 mmap;MD5 是全文件哈希;小文件逐个写、逐个 fsync。

#### 5.1.2 改造点一:动态自适应缓冲区(P-01)

- **目标**:IO 吞吐提升 15-30%(小文件密集场景)
- **方案**:在 `IoOptimizer` 内加 `AdaptiveBufferManager` 滑动窗口(10 个样本),按平均写延迟调缓冲区:延迟 >1ms → ×1.5(上限 8MB);延迟 <100µs → ÷1.2(下限 4KB)。**复用现有对象池**,只改池内 buffer 尺寸策略,不新建分配路径。
- **关键约束**:并发协程共享同一缓冲区尺寸策略时必须用 `AtomicInteger` 或锁保护调整点;调整频率限制为每 100 次写最多 1 次,避免抖动。
- **TDD**:先写 `AdaptiveBufferManagerTest`(延迟注入序列 → 期望缓冲区轨迹),再实现。
- **回退**:`BuildConfig` 或系统属性开关 `io.adaptiveBuffer=false` 时回到静态策略。

#### 5.1.3 改造点二:mmap 大文件零拷贝(P-02)

- **目标**:>16MB 大文件复制速度提升 50-100%(游戏 pak/obb 文件是主场景)
- **方案**:在 `fastCopy` 入口按 `source.length()` 分流:≥16MB → `RandomAccessFile` + `FileChannel.map(READ_WRITE)` + `MappedByteBuffer.force()`;否则走现有 `transferTo`。**注意 Android 上 mmap 受 `vm.max_map_count` 限制,同任务并发 mmap 数必须 ≤32,用信号量控制**;map 完必须显式 unmap(现有 `unmap()` 已有先例,`IoOptimizer.kt:103`)。
- **风险**:Shizuku 模式下目标文件在远端进程,mmap 不可用——**只对 NATIVE/ROOT 模式启用**,Shizuku 模式保持现状。这是文档明确要求的分支条件,实施者勿漏。
- **TDD**:`IoOptimizerMmapTest`(Robolectric 下用临时目录验证 16MB 阈值分流与字节级一致性)。
- **回退**:阈值常量改为 `Long.MAX_VALUE` 即整体禁用。

#### 5.1.4 改造点三:小文件聚合批写(P-03)

- **目标**:<1KB 小文件吞吐提升 3-5x(游戏资源常有数万个小配置文件)
- **方案**:新增 `SmallFileBatchWriter`:批内最多 64 个文件或累计 1MB 触发 flush;flush 时顺序写完所有目标后**单次** `fd.sync()`。挂在 `NormalCopyOrchestrator` 的批次循环里(`FileStatistics` 已产批次,直接消费)。
- **关键约束**:聚合期间取消信号必须可中断(flush 前检查 `isStopped`;失败时整批按现有逐文件错误路径回报,不吞错);内存上限 = batchSize × 1MB 硬编码防护。
- **TDD**:`SmallFileBatchWriterTest`(边界:63/64/65 个文件、跨 1MB 阈值、批中取消、批中失败)。

#### 5.1.5 改造点四:抽样哈希增量比较(P-04)

- **目标**:大文件哈希比较耗时降低 80%
- **方案**:`FileHasher` 增加 `samplingHash(file)`:<1MB 全量 MD5;否则取头/中/尾三段各 64KB 拼接后哈希。`needsUpdate` 的调用方按"抽样相等 → 再全量确认"两级策略(抽样不同必更新;抽样相同才全量比对),避免抽样碰撞导致漏更新。
- **TDD**:`FileHasherSamplingTest`(构造仅尾部 1 字节不同的两个文件 → 必须判为需更新;头中尾全同但中部不同 → 必须判为需更新)。

#### 5.1.6 性能基线与验收(不可跳过)

- **基线**:在新提交的 `docs/benchmarks/V14-baseline.md` 中记录:三类代表场景(100×1KB 小文件 / 1×500MB 大文件 / 混合 1000 文件)在 NATIVE 与 ROOT 模式下的耗时,跑 5 次取中位数。用 `adb shell am start` + 应用内 APM 面板读数。
- **验收门禁**:每个优化点合入后,对应场景必须 ≥ 基线的预期增益,且其余场景劣化 ≤5%;不达标就回退该点。
- **设备矩阵**:至少 1 台 eMMC 中端机 + 1 台 UFS 旗舰机(条件允许加 1 台 Root 机)。

## 12. 风险、阻塞项与待拍板问题

### 12.1 当前阻塞项(实测)

1. **无 Android 设备/模拟器连接**:性能基线、TalkBack 走查、悬浮球手测、备份恢复手测均需真机。实施前用 Android Studio 设备管理器起一个 API 34+ 模拟器(Shizuku 相关路径需真机,模拟器只能覆盖 NATIVE 模式)。
2. **Robolectric 对 mmap 的支持度未知**:P-02 的单测可能受限于影子实现,必要时 mmap 用设备上的 instrumented test(`androidTest`)验证,单测只覆盖分流逻辑。
3. **gradlew 需要 JAVA_HOME**:本机双 JDK 并存,确认 `JAVA_HOME` 指向 JDK 17(AGP 8.7 要求),否则构建直接失败。

### 12.2 需要拍板的产品问题

| # | 问题 | 建议默认值 |
|---|------|-----------|
| 1 | 备份是否默认强制开启(替换前自动备份)? | 是(当前 Worker 已硬编码开启,保持) |
| 2 | 备份保留数量暴露给用户? | 是,V14.1.0 设置项(3-30,默认 10) |
| 3 | 悬浮球无任务时完全隐藏还是边缘小圆点? | 边缘小圆点(可发现性更好) |
| 4 | OTA 更新失败重试次数上限? | 3 次,超过转手动 |
| 5 | V15 隐匿增强的产品边界(对抗厂商检测的合规性)? | 明确拒绝越界能力,只做时间戳随机化等中性功能 |
| 6 | `QUERY_ALL_PACKAGES` 权限是否保留? | 若目标应用选择依赖应用列表则保留,否则收敛为 `<queries>` 白名单(Play 审核友好;侧分发无影响) |

### 12.3 给实施 AI 的红线(再次强调)

1. **严禁跳过 Phase A 直接做 V14**——71 个未提交文件是当前最大风险源。
2. **严禁在任何优化点未达增益预期时保留该改动**——回退是交付的一部分。
3. **严禁删除任何测试来"让构建变绿"**——测试失败只允许修实现或(经确认测试本身错了)修测试。
4. **严禁在 M1-M4 未全绿时执行 M5**——主布局迁移是单行道,回滚成本最高。
5. **每完成一个任务,同步更新 `project_specs.md` 与 CHANGELOG**——文档漂移是本项目历史上反复发生的债务。
