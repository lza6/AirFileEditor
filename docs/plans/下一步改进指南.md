## 4. 项目架构和关键链路

### 4.1 系统边界与模块职责

```
:app (UI) → :data (Repository实现) → :domain (实体/用例/接口) ← :core (基础设施)
                                                                  ↑
                                            (Shizuku/Worker/Performance/Manager/Security)
```

- `:domain`：纯 JVM，定义 `TaskPhase` 7 态、`ConfigRepository`、`TaskController` 接口、UseCase。禁止依赖 Android。
- `:data`：`ConfigRepositoryImpl` 封装 Manager 逻辑、`PreferencesManager`、`ReplaceHistoryManager`。**注意：`:data` 通过 `ConfigRepositoryImpl:36` 持有 `TaskControllerImpl`。**
- `:core`：Shizuku AIDL、Worker/Orchestrator、IoEngine、解压器、安全校验、AppLogger、性能监控。
- `:app`：Activity、Compose MVI、ViewBinding/DataBinding 混合。

### 4.2 关键用户路径（替换）

```
用户操作 → ReplacingViewModel(MVI) → repository.startReplace(ConfigRepository, enqueueUniqueWork KEEP)
        → FileReplaceWorkerV2 → Normal/Root/Shizuku Orchestrator → CopyStrategy → 复制
        → VerificationManager.verify (verifiedCount==totalFiles) → 终态反馈
```

**状态流（本轮发现的关键风险）**：

- `TaskControllerImpl` 为普通 class（非 object），`_state = MutableStateFlow(TaskState())` 为**实例级**（`TaskControllerImpl.kt:16-17`）。
- 生产代码中 `TaskControllerImpl()` 被实例化了 7 处，彼此独立：
  - `FileReplaceWorkerV2:87` — **Worker 真正 `updateState` 的唯一实例**（doWork 内 `taskController.updateState/finish/fail`）
  - `ConfigRepositoryImpl:36` — `:data`，`getTaskProgress()` 返回 `taskController.state.map{}`（UI `ReplacingViewModel` 订阅此流）
  - `NormalCopyStrategy:31` / `RootCopyStrategy:33` / `ShizukuCopyStrategy:34` — 策略各自新建（未实际调用 updateState，疑似冗余）
  - `ConfigRepositoryProvider:20` — `:app` 单例，悬浮球订阅
  - `MainViewModel:66` — 孤儿 VM，无任何外部引用
- **Worker 与 UI 订阅的是不同 `TaskControllerImpl` 实例 → `StateFlow` 不共享**。该问题属静态确认，实际影响需实机验证（标记 `待验证`）。详细分析见 §8.5。

**错误流**：复制失败 → Orchestrator 失败 → Worker `fail` → 终端反馈 → 可重试。解压失败 → fail-closed，不留半成品。

**权限流**：PermissionController 检测 Root/Native/Shizuku → Omni-Mode 物理验证 → 模式选择。

**安全链路**：
- 目标路径唯一入口 `PathConstants.resolveTargetFile()` + `isSafeTargetPath` + `shellEscape`
- 压缩包条目先经 `ArchiveEntryValidator` 完整校验再写入；RAR 等不支持格式 fail-closed
- Shizuku AIDL 命令/路径白名单 fail-closed
- 复制完成强制 `VerificationManager.verify`

### 4.3 外部依赖

Shizuku 13（Binder 跨进程）、Zip4j / Commons-Compress（解压）、WorkManager（后台）、OkHttp（更新检查/云规则 `RuleEngine.fetchCloudRules`）、DataStore（偏好）。

## 8. 根本原因分析

### 8.1 P0-01 任务进度状态源断裂（本轮最大新发现）

- **表面现象**：替换任务运行时，UI 可能不显示实时进度/结果；最终结果反馈依赖 `ReplacingViewModel` 手动置状态，而非来自任务状态流。
- **直接原因**：`TaskControllerImpl` 是普通 class（非 object），`_state` 是实例级（`TaskControllerImpl.kt:16-17`）。生产代码 7 处各自 `TaskControllerImpl()`，彼此是不同对象：
  - `FileReplaceWorkerV2:87` 的 controller 是 `doWork` 里 `updateState/finish/fail` 写入的唯一目标；
  - `ConfigRepositoryImpl:36` 的 controller 被 `getTaskProgress()`（`ConfigRepositoryImpl.kt:92-103`）返回给 `ReplacingViewModel`（`ReplacingViewModel.kt:42` 订阅）；
  - 二者为**不同实例**，`StateFlow` 天然不共享。
- **系统性原因**：V15/V16 用 `TaskControllerImpl()` 直接实例化（而非共享单例或经 DI 注入），且 `ConfigRepositoryProvider` 只覆盖了悬浮球，没有把 Worker、ConfigRepositoryImpl、策略统一到同一实例。`TaskController` 接口虽定义为"任务状态唯一权威源"，但实现层的实例化方式破坏了"唯一"。
- **影响半径**：核心用户路径"替换 → 进度 → 结果"的实际成功率存疑；`cancelReplace`（`ConfigRepositoryImpl:81-86`）调用 `taskController.cancel()` 操作的是 UI 侧实例，而 Worker 的取消由 `WorkManager.cancelUniqueWork` 触发（`FileReplaceWorkerV2:118` 是 Worker 自己的实例）——两条取消路径也可能不同步。
- **相关文件**：`core/.../TaskControllerImpl.kt`、`core/.../FileReplaceWorkerV2.kt:87`、`data/.../ConfigRepositoryImpl.kt:36`、`core/.../{Normal,Root,Shizuku}CopyStrategy.kt`、`app/.../ConfigRepositoryProvider.kt:20`、`app/.../MainViewModel.kt:66`。
- **当前证据**：静态确认 7 处实例化 + `TaskControllerImpl` 为实例级状态。
- **尚未确认的假设**：实机上进度是否真的不实时更新（需真机/模拟器跑一个替换任务观察进度条从 0 变化到完成，以及失败时 UI 是否显示失败终态）。
- **最小验证方法**：在模拟器（API 35）上选一个小包执行替换，观察 `ReplacingViewModel` 订阅的进度是否随 Worker 更新；或写一个单测验证"Worker 创建的 controller 与 ConfigRepositoryImpl 创建的 controller 是否为同一对象"（当前必为 false）。

### 8.2 P1-01 真实覆盖率 27.7% / 30.8%

- **表面现象**：`jacocoTestReport` 已真实产出 XML，但门禁范围内行覆盖仅 27.7%。
- **直接原因**：门禁排除了大量 UI 层类（`jacocoClassFilters` 排除 `ui/components`、`ui/compose`、`MainActivity`、`FloatingBall*` 等，`app/build.gradle.kts:97-119`）；纳入统计的都是 `:app` 业务逻辑，而 `:core`/`:domain` 的覆盖率默认不进 `:app` 的 Jacoco 报告（报告的 `classDirectories` 只含 `app/tmp/kotlin-classes`，`build.gradle.kts:130-136`）。
- **系统性原因**：历史"80%"是 V9 时代的设定，从未真正执行（V4 已证门禁 SKIPPED）；本轮修复后才暴露真实基线，于是用棘轮阈值 0.27/0.30 放行。
- **影响半径**：`checkQuality` 用 27.7% 作为当前门槛，任何新增业务代码若覆盖被稀释会触发阈值；`codecov` 上传的 XML 实际只含 `:app`，CI 的覆盖统计不完整。
- **当前证据**：XML 根级 LINE covered=236/missed=615、BRANCH covered=77/missed=173。
- **尚未确认的假设**：`:core`/`:domain` 的真实覆盖率未单独统计（不在本报告的 `classDirectories` 内）。
- **最小验证方法**：为 `:core`/`:domain` 单独生成 Jacoco 报告，或在聚合任务中将三模块的 `classDirectories` 合并统计，获得全局真实覆盖。

### 8.3 P1-02 解压安全链路测试缺口

- **表面现象**：`UniversalExtractor`(611 行) 已有 `UniversalExtractorSecurityTest`(5 用例)，但 `ExtractManager`(559 行) / `ArchiveManager`(466 行) 无测试。
- **直接原因**：V13 安全重构只为 `UniversalExtractor` 与校验器补了单测，遗漏了另外两个解压器入口。
- **系统性原因**：解压器依赖 Android `context`/`DocumentFile`，单测成本高，被长期搁置。
- **影响半径**：若 `ExtractManager`/`ArchiveManager` 存在绕过 `ArchiveEntryValidator` 的分支，无测试拦截，CLAUDE.md 的"先完整校验再写入"红线无实测保障。
- **最小验证**：为两者各建测试，覆盖合法条目全写、`..` 拒绝、绝对路径拒绝、重复条目拒绝、RAR fail-closed、staging 失败清理。

### 8.4 P1-03 密码历史残留

- **表面现象**：`build.gradle` 明文已改 `loadKeystoreProperties()` 读取，但 `git log -S "tfgwj2026"` 仍命中 3 个提交。
- **直接原因**：V15 直接内联密码，V16.1 外置了文件内容但未清理历史。
- **系统性原因**：未区分"本地凭据"与"仓库公开内容"，未做历史清理。
- **影响半径**：仓库公开即泄露口令，攻击者可签名冒充应用。JKS 文件本身在 `%LOCALAPPDATA%` 未提交，风险限于口令泄露。
- **注意**：改写 git 历史（`filter-repo`/`filter-branch`）属不可逆高风险操作，需用户明确授权；本指南仅记录建议。

### 8.5 P2-04 / P2-05 死代码与冗余实例化

- **MainViewModel**：190 行，`MainActivity` 实际用 `ReplacingViewModel`（`MainActivity.kt:64`），`MainViewModel` 无任何引用，是遗留死代码。`MainViewModel.kt:66` 还冗余新建 `TaskControllerImpl()`（浪费，且加剧状态源分散）。
- **3 个 CopyStrategy**：各自新建 `TaskControllerImpl()`（`NormalCopyStrategy:31`/`RootCopyStrategy:33`/`ShizukuCopyStrategy:34`），但这些 controller 从未被策略调用 `updateState`，实际状态更新由 `Worker` 的 controller 完成——策略内的 controller 是彻头彻尾的冗余。

### [P0-01] 收敛 TaskController 为共享单例，修复状态源断裂

- 优先级：**P0**
- 风险等级：L2（触及任务状态权威，需隔离实施 + 实机验证回归）
- 类型：缺陷修复
- 当前状态：7 处独立实例化；Worker 与 UI 状态流不共享
- 证据：`TaskControllerImpl.kt:16-17`（实例级 `_state`）；`FileReplaceWorkerV2:87`；`ConfigRepositoryImpl:36`；`{Normal,Root,Shizuku}CopyStrategy`；`ConfigRepositoryProvider:20`；`MainViewModel:66`
- 根本原因：`TaskControllerImpl` 普通 class 被 7 处 `new`，无共享单例
- 用户价值：替换任务进度实时刷新、失败/取消终态与真实结果一致
- 技术价值：真正落实"任务契约走 ConfigRepository（唯一权威）"红线
- 推荐方案（三选一，按侵入从小到大）：
  1. **最小改动**：`ConfigRepositoryImpl` 改为持有**同一个** `TaskController` 实例——将 `ConfigRepositoryImpl` 构造时注入的 controller（经 `ConfigRepositoryProvider.getTaskController()`）传给 Worker 与各策略（需改 `FileReplaceWorkerV2`、3 个策略、`ConfigRepositoryImpl` 构造器，把实例源头统一到 `ConfigRepositoryProvider`）。
  2. **推荐**：在 `:core` 层提供 `TaskControllerProvider`（object，懒初始化），`ConfigRepositoryImpl`/Worker/策略都经它取同一个实例；`ConfigRepositoryProvider`（app 层）改为委托给 `:core` provider。
  3. **大改**：引入 Hilt/Koin DI（项目明确无 DI 框架，改动大、不推荐）。
- 为什么选择方案 1/2：项目无 DI 框架、`ConfigRepositoryProvider` 已存在可复用，最小侵入即可统一实例。
- 是否可复用现有实现：是，复用 `ConfigRepositoryProvider` / 新增 `:core` 的 `TaskControllerProvider`。
- 不推荐的替代方案：方案 3（Hilt/Koin）改动面大，与项目"无框架手动 DI"约定冲突。
- 涉及文件：`core/.../TaskControllerImpl.kt`（新增 provider 或改为共享）、`core/.../FileReplaceWorkerV2.kt:87`、`core/.../{Normal,Root,Shizuku}CopyStrategy.kt`、`data/.../ConfigRepositoryImpl.kt:36`、`app/.../ConfigRepositoryProvider.kt:20`、`app/.../MainViewModel.kt:66`（孤儿）
- 上游依赖：无
- 下游影响：替换进度流、取消流、终态反馈一致性
- 数据和接口影响：无（不改 `ConfigRepository` 接口）
- 安全与隐私影响：无
- 建议实施步骤：
  1. 先在 `:core` 新增 `object TaskControllerProvider { fun get(): TaskController }`（懒初始化单例）
  2. `FileReplaceWorkerV2`、`ConfigRepositoryImpl`、3 个策略全部改经 `TaskControllerProvider.get()`
  3. `ConfigRepositoryProvider`（app）改为委托 `:core` provider（或删除 app 层冗余）
  4. 删除 `MainViewModel`（孤儿）及其冗余 controller
  5. **实机验证**：模拟器执行替换任务，确认进度条从 0 随 Worker 更新到 100%，失败/取消终态正确
- TDD/测试清单：
  - 单测：`TaskControllerProvider` 返回同一实例（`assertSame`）
  - 单测：`ConfigRepositoryImpl.getTaskProgress()` 观察到的 flow 与 Worker 写入的 controller 同一（可注入 fake controller 验证）
  - 实机：替换任务进度实时性、失败/取消终态
- 验收标准：生产代码 `TaskControllerImpl()` 直接实例化仅剩 provider 一处（或 0 处）；实机替换进度实时刷新；`ReplacingViewModel` 收到的终态与 Worker 实际结果一致
- 回归检查：现有 TaskControllerImplTest（8 用例）、三 Orchestrator 测试不回归
- 回滚方案：还原为 7 处分散实例化（保留原版本）
- 预估复杂度：M（2-3 天）
- 仍需确认的问题：实机进度是否确实不实时（本轮未验证）；是否保留 `ConfigRepositoryProvider`（app 层）还是统一到 `:core`

## 14. 性能、稳定性和长期运行

- **冷启动**：`MainLifecycleCoordinator` 用 `delay` 序列（300/1000/2000ms）错峰加载。无实测冷启动数据（P3-01 建基准）。

- **状态泄漏**：`ConfigRepositoryImpl` / Worker / 策略各自持有独立 controller → 多个 `StateFlow` 实例，长期可能造成订阅泄漏与状态不同步（P0-01 相关的稳定性影响）。

## 17. TDD 与测试改进指南

**当前框架与运行**：JUnit4 + MockK + Turbine + coroutines-test + Robolectric；`Fake` 优先于 Mock；`gradlew :app:testDebugUnitTest :domain:test :core:testDebugUnitTest`。

**本轮真实运行**：三模块 `--rerun-tasks` → BUILD SUCCESSFUL（1m26s，68 任务全部执行），208 个 `@Test` / 28 个测试文件。

**关键测试缺口**（优先级排序）：
1. **P0-01 状态源一致性**：验证"Worker 与 ConfigRepository 观察同一 controller"（可注入 fake controller 断言 `assertSame`）。修复后必须有此单测锁定。
2. **P1-02 解压安全链路**：ExtractManager/ArchiveManager 合法+穿越+绝对路径+重复+RAR fail-closed。
3. **P1-01 覆盖率完整性**：`:core`/`:domain` 覆盖率纳入统计后，预期全局覆盖略降（因纳入更多未测代码），需建立新基线。
4. **FileTimeModifier 底层**（P2）：随机/锁定/应用时间戳。
5. **权限路径**：PermissionController 三种模式选择边界（Root/Native/Shizuku 物理验证失败分支）。
6. **并发/重复提交**：`enqueueUniqueWork(KEEP)` 下 UI 重复点击、任务并发。

**测试数据与隔离**：Fake 优先；解压测试用内存构造归档；避免 `mockkStatic`（V15 已因栈溢出弃用）。

**覆盖率策略**：不以全局 80% 为唯一目标（实际当前 27.7%）。以本轮真实基线与棘轮门禁为准：核心安全/状态机逻辑场景完整；未来变更代码高覆盖；全局不低于当前基线并逐步提升。覆盖无法覆盖的（UI 交互、权限物理验证、真机 Shizuku、进度实时性）用 E2E/实机补足。

## 21. Red Team 事前反证

从"六个月后本改进计划失败"倒推最可能原因：

1. **把"E2E 通过"当成"进度流已验证"**——V16 E2E 只验证了 UI 渲染标题，未验证替换进度实时性，从而掩盖了 P0 状态源断裂。**证伪实验**：任何 E2E 报告必须含"替换任务期间进度条从 0 变化到完成 + 失败/取消终态正确"的断言，缺一不可。
2. **P0 修复方案因为"侵入 ConfigRepositoryImpl 构造器"被搁置**——若担心改构造签名影响 `ReplacingViewModelFactory` 而拖延，P0 永不落地。**证伪实验**：限定 T1（实机验证）+ T2（收敛单例）一轮完成，不改 `ConfigRepository` 接口、只改实现层实例来源，降低风险。
3. **真实覆盖率仅 27.7% 触发"补测试卡关"**——若为赶 80% 而下调门禁或静默排除大量类，是用门禁换绿色的反模式。**证伪实验**：任何阈值下调须留审计记录与理由；扩展覆盖到三模块时，预期全局覆盖会因纳入未测代码而下降，这是正常的、须接受并登记。
4. **git rewrite 历史导致仓库损坏或协作者提交丢失**——L3 操作未充分备份。**证伪实验**：先完整备份 + 克隆副本演练 + 沟通，再操作主仓库。
5. **文档对齐被当作"可推迟的 P2"无限搁置**——CHANGELOG/README/project_specs 三份文档已连续两版失实，持续误导后续版本规划。**证伪实验**：文档对齐作为 P2 但绑定在版本发布前，不允许发布时仍带失实文档。

**结论**：
- 可直接开始：T1（实机验证状态源）、T3（轮换口令）、T9（文档对齐）、T5/T6（解压测试）
- 应先实验再实施：T2（收敛单例，需 T1 结论）、T4（git rewrite）、T7（覆盖扩展）
- 应降低优先级：P2-05 错误上报（需隐私评估）、P3 全项
- 当前不建议实施：V17 批量操作 UI 应在 T2 修复后启动（避免建立在不可靠进度反馈上）
