## 1. 第一性原理：项目本质与升级哲学

### 1.1 项目的本质是什么？

用户视角：**"把目标游戏/应用的 `Android/(data|obb)` 目录文件，用我选的包，安全、无痛、尽快地替换掉。"**

拆解成不可再分的底层要素：

| 底层要素 | 本质 | 当前实现 |
|---|---|---|
| **权限通道** | 用什么方式拿到读写受限目录的能力 | Omni-Mode (Root/Native/Shizuku)，`PermissionChecker` 智能检测 |
| **传输效率** | 把字节从 A 搬到 B 要多久 | `IoEngine` (mmap/缓冲流/小文件 + 增量比对) |
| **数据安全** | 搬错了/搬坏了怎么办 | `ArchiveEntryValidator` / `ArchiveSafetyGuard` / `VerificationManager` / `BackupManager` |
| **任务编排** | 一个长任务如何可靠执行、可恢复、可反馈 | `TaskController` + `FileReplaceWorkerV2` + `WorkManager` |
| **用户体验** | 小白会不会用、点没点反馈、卡不卡 | Compose MVI + 反馈组件 |

**升级哲学 = 在每一层把"能用"推向"顶尖"**：
- 权限通道 → 更快感知、更稳授权、更准降级
- 传输效率 → 逼近硬件极限、内存可控、自动降级
- 数据安全 → 从"防穿越"到"防压缩炸弹/防伪造/防半成品"
- 任务编排 → 中断恢复、断电续跑、可追溯审计
- 用户体验 → 从"能点"到"有反馈"到"懂用户"

### 1.2 "从 1 → N"的具体含义

- 现有代码已经**从 0 走到了 1**（功能闭环、四层架构、225 个测试、质量门禁）。
- 本指南的目标是**在不动摇骨架的前提下**（用户明确禁止大重构、禁止造轮子），做**手术式迭代**：清残留、补短板、扩能力、上性能、固安全。
- 每个版本都必须**可独立交付、可独立验证、可回滚**，落地顺序满足：

```
先清债务 → 再固质量 → 后加能力 → 最终提性能/体验/安全
```

### 1.3 三条不可违反的红线（来自 CLAUDE.md，任何迭代必须守住）

1. **`TaskPhase` 是任务状态唯一权威源**：`domain/model/DomainModels.kt` 的 7 态；终态不算 `isReplacing`。
2. **任务契约只走 `ConfigRepository`**：`enqueueUniqueWork(KEEP)`；`cancelReplace` 同时取消 + 置 CANCELLED；`dismissReplaceResult` 只重置不取消。
3. **目标包名禁止回退**：唯一来源 `PreferencesManager.appPackageName` → `ReplacingState.targetPackage`；空/非法包名 fail-closed。
4. **目标路径唯一映射入口**：`PathConstants.resolveTargetFile()`；必须落在 `/storage/emulated/0/Android/(data|obb)/<pkg>/`，经 `isSafeTargetPath`，shell 参数 `shellEscape`。
5. **压缩包先完整校验后写入**：`ArchiveEntryValidator` 拒绝 `..`/绝对路径/盘符/NUL；不支持格式 fail-closed 不留半成品。
6. **复制完成后强制验证**：三个 Orchestrator 必须跑 `VerificationManager.verify`，`verifiedCount != totalFiles` 即失败。

> 任何 V17+ 改动若触碰上述红线，必须以保证一致性为前提，且要先跑被锁定的单测。

  - `rg "HighPerformanceIoEngine"` 全仓确认无运行时代码引用后才删除源文件。

#### V17.2 删除硬编码包名残留

- 删除 `AppConstants.DEFAULT_GAME_PACKAGE_NAME` / `ALTERNATIVE_GAME_PACKAGE_NAMES`。

- 确认 `rg "ALTERNATIVE_GAME_PACKAGE_NAMES|DEFAULT_GAME_PACKAGE_NAME|PUBG_PACKAGE_NAME"` 无引用。

#### V17.3 删除未接线的死 Intent

- 逐项核对 `ReplacingIntent` 与 `ReplacingViewModel.handleIntent()`，删除落入 `else -> {}` 无实体逻辑的 Intent。

#### V17.4 清理 `FileReplaceWorkerV2` 死代码

- 删除 `:253-271` 被注释的历史写入块。
- 核实 `updateProgressState` 是否无调用；若确无引用则删除。

#### V17.5 复核状态机边界（回归确认）

### V18 — 性能引擎 2.0

**P0 · 中高量级 · 纯性能**

**背景**：当前 `IoEngine` 大文件 mmap 一次性映射有 OOM 风险；无内存水位感知；小文件未聚合。这三个是"从 1 到 2"性能跃迁的关键。

#### V18.1 分块 mmap（防止大文件 OOM）

- 将 `mmapCopy` 的一次性 `map(0,size)` 改为**分块**（如每块 32-64MB）循环映射 + 块内 `put`，块间 `transferTo` 或重复映射。
- 增加开关 `MMAP_CHUNK_SIZE` / `MMAP_MAX_FILE_SIZE`：超过阈值改用流式写（`FileChannel` + `ByteBuffer` 轮询）。
- 保留降级路径（失败→自适应缓冲流→返回 0）。

#### V18.2 内存水位守护（`MemoryPressureGuard`）

- 新增 `core/performance/MemoryPressureGuard`：读取 `ActivityManager.getMemoryInfo`，计算 `availMem/totalMem`，输出压力等级（LOW/MEDIUM/HIGH）。
- `IoEngine.parallelProcess` 在高压力下：降低 `concurrency`、禁用 mmap、减小缓冲。
- 接入 `AdaptiveBufferManager` 的扩容 clamp，联动内存水位。

#### V18.3 小文件聚合批量写入

- 新增 `SmallFileBatchWriter`：<32KB 文件攒批同刷（如 64 个一刷 / 4MB 一桶），减少系统调用。
- 与 `IoEngine.fastCopy` 的小文件分支协同，保留单文件接口向后兼容。

#### TDD 清单（V18）

1. `IoEngineTest` 增补：分块 mmap 边界（块大小整除/不整除/文件=块大小/文件=0）。
2. 新增 `MemoryPressureGuardTest`：mock memoryInfo 产出 LOW/MEDIUM/HIGH + 降级决策。
3. 新增 `SmallFileBatchWriterTest`：批量刷盘/半桶 flush/失败部分回滚/总量正确。
4. `AdaptiveBufferManagerTest` 增补扩容上限 clamp 用例。

#### 验收标准

- [ ] `.\gradlew.bat testDebugUnitTest` 全绿；JaCoCo 行覆盖 ≥80%。
- [ ] 大文件复制（构造 >500MB 临时文件）压测不 OOM（记录 `dumpsys meminfo`）。
- [ ] `checkQuality` 通过。

**风险**：分块 mmap 对设备文件系统依赖较高 → 保留降级；压测文档披露设备差异。
