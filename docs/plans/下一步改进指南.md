## 2. 执行摘要

**当前阶段**：V16 任务引擎收口已闭环并合并入 main。项目已完成 Clean Architecture 四层拆分、MVI 状态管理、三模式 Orchestrator、安全 fail-closed 体系、IoEngine 统一引擎与 161 个单测用例。架构骨架成熟，**适合进入以"可信度与可维护性"为优先的下一阶段**，而非继续扩张功能。

**最值得保留的优势**：
- Clean Architecture + DDD 四层（`:app → :data → :domain ← :core`），`:domain` 纯 JVM 无 Android 依赖
- 安全体系（`ArchiveEntryValidator` / `ArchiveSafetyGuard` / AIDL 白名单 / fail-closed）被单测锁定
- 任务状态机 7 态（`TaskPhase`）成为唯一权威源，终态语义清晰
- `TaskController` 接口化取代全局单例，`AppLogger` 已加事件流（`SharedFlow`）
- 质量门禁（Detekt + Ktlint + JaCoCo）已注册，CI/CD 流水线存在

**最重要的 5 个问题**（详见第 7、8 节）：
1. **P1 — Jacoco 覆盖率门禁实际失效**：`jacocoTestReport` 的 `executionData` 指向遗留路径 `app/build/jacoco/testDebugUnitTest.exec`，而 AGP 8.7.3 实际输出到 `app/build/outputs/unit_test_code_coverage/debugUnitTest/testDebugUnitTest.exec`，导致报告/验证任务每次都 `SKIPPED`。"checkQuality 全绿"与"行覆盖≥80%"的结论失真。
2. **P1 — CI 只跑 `:app` 测试**：`.github/workflows/ci.yml` 的 `testDebugUnitTest` 仅覆盖 `:app`，而 `:core`（15 个测试文件）与 `:domain`（4 个）在 CI 中不运行，本地验证范围与 CI 不一致。
3. **P1 — 硬编码签名密码已提交进 git 历史**：`app/build.gradle.kts` 中 `storePassword`/`keyPassword = "tfgwj2026"` 自 commit e3d352b 起被跟踪。
4. **P1 — 解压核心链路无测试**：`ExtractManager`(559行)/`UniversalExtractor`(611行)/`ArchiveManager`(466行) 共 1636 行安全红线代码，无任何对应测试；项目 CLAUDE.md 声称"所有解压路径必须先完整校验条目再写入"，但校验后的写入逻辑未被测试锁定。
5. **P2 — DI 残留**：`FloatingBallManager.kt:291` 直接 `TaskControllerImpl()` 硬编码实例化（V15 注释自认"长期应改为通过 ConfigRepository 注入"）；`AppLogger` 仍为全局 object 单例（417 行）。

**下一阶段核心目标**：
1. 修复 Jacoco 门禁使其真正运行（P1），建立真实可核验的覆盖率基线；
2. 统一 CI 与本地验证范围，让 `:core`/`:domain` 测试进入 CI（P1）；
3. 从 git 历史中移除签名密码，改为本地/环境注入（P1，需谨慎操作）；
4. 为解压安全链路补测试（P1）；
5. 收敛 DI（FloatingBallManager + AppLogger）（P2）；
6. 之后进入 V17 文件浏览器引擎（P2，功能扩张）。

**推荐总体实施顺序**：先修 P1 可信度（门禁/CI/密码/测试），再收 P2 可维护性（DI），再做 V17 功能。**不要跳过 P1 直接进入 V17 功能开发**——在覆盖率门禁失效、CI 范围不全的前提下扩张功能，会持续累积不可验证的技术债。

**当前最大交付风险**：在不修复 Jacoco 门禁的情况下，后续所有"覆盖率达标""checkQuality 全绿"的声明都不可核验，V17+ 的功能验证将建立在不可靠的地基上。

## 4. 项目架构和关键链路

### 4.1 系统边界与模块职责

```
:app (UI) → :data (Repository实现) → :domain (实体/用例/接口) ← :core (基础设施)
                                                                  ↑
                                            (Shizuku/Worker/Performance/Manager/Security)
```

- `:domain`：纯 JVM，定义 `TaskPhase` 7 态、`ConfigRepository`、`TaskController` 接口、UseCase。禁止依赖 Android。
- `:data`：`ConfigRepositoryImpl` 封装 Manager 逻辑、`PreferencesManager`、`ReplaceHistoryManager`。
- `:core`：Shizuku AIDL、Worker/Orchestrator、IoEngine、解压器、安全校验、AppLogger、性能监控。
- `:app`：Activity、Compose MVI、ViewBinding/DataBinding 混合。

### 4.2 关键用户路径（替换）

```
用户操作 → ReplacingViewModel(MVI) → startReplace(ConfigRepository, enqueueUniqueWork KEEP)
        → FileReplaceWorkerV2 → Normal/Root/Shizuku Orchestrator → IoEngine 复制
        → VerificationManager.verify (verifiedCount==totalFiles) → 终态反馈
```

**状态流**：`TaskController.state: StateFlow<TaskState>`，7 态机，终态（COMPLETED/FAILURE/CANCELLED）不算 `isReplacing`。

**错误流**：复制失败 → Orchestrator 失败终态 → UI 终态摘要卡 → 可重试。解压失败 → fail-closed，不留半成品。

**权限流**：PermissionController 检测 Root/Native/Shizuku → Omni-Mode 物理验证 → 模式选择。

**安全链路**：
- 目标路径唯一入口 `PathConstants.resolveTargetFile()` + `isSafeTargetPath` + `shellEscape`
- 压缩包条目先经 `ArchiveEntryValidator` 完整校验再写入；RAR 等不支持格式 fail-closed
- Shizuku AIDL 命令/路径白名单 fail-closed
- 复制完成强制 `VerificationManager.verify`

### 4.3 外部依赖

Shizuku 13（Binder 跨进程）、Zip4j / Commons-Compress（解压）、WorkManager（后台）、OkHttp（更新检查/云规则 `RuleEngine.fetchCloudRules`）、DataStore（偏好）。

## 8. 根本原因分析

### 8.1 P1-01 Jacoco 覆盖率门禁失效

- **表面现象**：`checkQuality` 报告 BUILD SUCCESSFUL，但 `jacocoTestReport` / `jacocoTestCoverageVerification` 每次 SKIPPED，无任何覆盖率结果生成。
- **直接原因**：`app/build.gradle.kts:107` 自定义 `JacocoReport` 任务的 `executionData` 指向 `fileTree(buildDir) { include("jacoco/testDebugUnitTest.exec") }`——这是旧版 AGP 的产物路径。AGP 8.7.3 实际将 exec 写到 `app/build/outputs/unit_test_code_coverage/debugUnitTest/testDebugUnitTest.exec`（本轮已验证该文件存在且非空，275040 字节）。因指定目录不存在，`executionData` 为空 → Jacoco 任务无输入 → `SKIPPED`。
- **系统性原因**：V15/V16 的 CI 与门禁依赖"能跑绿"即通过的直觉，从未强制验证 Jacoco 是否真产出报告；`checkQuality` 的 SUCCESS 掩盖了覆盖验证未执行。
- **影响半径**：所有"覆盖率≥80%""checkQuality 全绿"的历史声明均不可核验；`codecov` 上传的 `jacocoTestReport.xml` 实际不存在，CI 的 codecov 步骤会静默失败。
- **相关文件**：`app/build.gradle.kts:78-138`（JacocoReport 定义）、`app/build.gradle.kts:113-138`（Verification 定义）、`.github/workflows/ci.yml`。
- **尚未确认的假设**：本地 `checkQuality` 绿色是 Detekt+Ktlint 通过的绿色，Jacoco 从未真正运行——需修复后复跑确认。
- **最小验证方法**：修正 `executionData` 路径（指向 AGP 实际输出目录）后，跑 `:app:jacocoTestReport` 应生成 HTML/XML 报告且不再 SKIPPED；`jacocoTestCoverageVerification` 应基于真实覆盖执行。

### 8.2 P1-02 CI 范围不全

- **表面现象**：CI 的 `test` job 只跑 `./gradlew testDebugUnitTest`（默认聚合 `:app` 及其依赖的测试），`:core`/`:domain` 的 19 个测试文件不进流水线。
- **直接原因**：`ci.yml:37` 未显式列出 `:core:testDebugUnitTest` / `:domain:test`。
- **系统性原因**：本地验证习惯三模块分开跑，但 CI 脚本未同步。
- **影响半径**：`core`（解压/安全/复制）与 `domain`（UseCase/状态机）回归无法在 CI 拦截；一旦 Jacoco 修复，CI 覆盖统计也不完整。
- **最小验证**：CI 命令改为 `./gradlew :app:testDebugUnitTest :core:testDebugUnitTest :domain:test jacocoTestReport`。

### 8.3 P1-03 硬编码签名密码

- **表面现象**：`storePassword`/`keyPassword = "tfgwj2026"` 明文在 `app/build.gradle.kts`，且随 commit e3d352b 进入 git 历史。
- **直接原因**：V15 为本地 release 签名方便直接内联密码。
- **系统性原因**：未区分"本地开发凭据"与"仓库公开内容"，未走环境变量/keystore.properties。
- **影响半径**：仓库被公开或推送到远程即泄露签名密钥口令，攻击者可签署冒充应用。
- **注意**：改写 git 历史（`filter-repo`/`filter-branch`）属不可逆高风险操作，需用户明确授权；本指南仅记录建议，不代执行。JKS 文件本身在 `LOCALAPPDATA` 未被提交，风险限于口令泄露。

### 8.4 P1-04 解压安全链路无测试

- **表面现象**：项目安全契约（ArchiveEntryValidator）有测试，但三个解压器（ExtractManager 559 / UniversalExtractor 611 / ArchiveManager 466）无任何测试。
- **直接原因**：V13 安全重构只补了校验器单测，未覆盖调用校验器后的实际写入逻辑。
- **系统性原因**：解压器依赖 Android `context`/`DocumentFile`，单测成本高，被长期搁置。
- **影响半径**：若校验器与写入逻辑之间出现回归（如某分支绕过校验），无测试拦截，且 CLAUDE.md 的"先完整校验再写入"红线无实测保障。
- **最小验证**：为 `UniversalExtractor` 写基于 `ArchiveEntryValidator` 的 Fake-archive 单测，覆盖：合法条目全写、含 `..` 拒绝、绝对路径拒绝、重复条目拒绝、RAR 不支持 fail-closed。

### 8.5 P2-01/P2-02 DI 残留（低优先级根因）

- **FloatingBallManager**：V15 迁移 `ReplaceProgressManager` 时用 `TaskControllerImpl()` 临时实例化替代，注释标注"长期应改为通过 ConfigRepository 注入"，至今未改。影响：难以单测、状态源被绕开 ConfigRepository 契约。
- **AppLogger**：全局 object 单例，V16 加事件流已缓解 UI 耦合，但整体仍是单例，测试需处理 Android 依赖。

### [P1-01] 修复 Jacoco 覆盖率门禁

- 优先级：P1
- 风险等级：L1（仅改构建脚本，不改业务）
- 类型：缺陷修复
- 当前状态：`jacocoTestReport`/`jacocoTestCoverageVerification` 均 SKIPPED
- 证据：`:app:jacocoTestReport --rerun-tasks` 输出 SKIPPED；`app/build.gradle.kts:107` executionData 指向 `jacoco/`，AGP 输出在 `outputs/unit_test_code_coverage/debugUnitTest/`
- 根本原因：executionData 路径与 AGP 实际输出路径错配
- 用户价值：恢复对"覆盖率达标"声明的可信度
- 技术价值：让质量门禁真实运行，暴露真实覆盖缺口
- 推荐方案：将 `executionData` 改为指向 `layout.buildDirectory.dir("outputs/unit_test_code_coverage/debugUnitTest")` 下的 `testDebugUnitTest.exec`；`dependsOn("testDebugUnitTest")` 保证先跑测试。
- 为什么选择该方案：最小改动，与 AGP 8.7.3 产物布局对齐，不动 Jacoco 版本。
- 是否可复用现有实现：是，仅改路径。
- 不推荐的替代方案：升级到 AGP 内建 `testCoverage` 报告机制（改动大、需迁移，风险更高，非本次必需）。
- 涉及文件：`app/build.gradle.kts:78-138`
- 上游依赖：无
- 下游影响：`checkQuality` 将真正执行覆盖验证，可能因真实覆盖不足而首次"红"——需以此建立真实基线
- 数据和接口影响：无
- 安全与隐私影响：无
- 建议实施步骤：
  1. 修改 `executionData` 路径为 AGP 实际输出目录
  2. `dependsOn("testDebugUnitTest")`
  3. `--rerun-tasks` 跑 `:app:jacocoTestReport` 确认生成报告
  4. 跑 `:app:checkQuality` 确认覆盖验证执行
- TDD/测试清单：无新测试；验证为构建任务输出
- 验收标准：`jacocoTestReport` 不再 SKIPPED 且生成 XML/HTML；`jacocoTestCoverageVerification` 实际执行（无论通过与否）
- 回归检查：`assembleDebug` 不受影响
- 回滚方案：还原两行路径改动
- 预估复杂度：S（半天）
- 仍需确认的问题：真实覆盖率当前是多少（修复后报告揭示）；若低于 80% 门禁需决策是否临时下调门禁或补测试

## 21. Red Team 事前反证

从"六个月后本改进计划失败"倒推最可能原因：

1. **把 Jacoco 门禁修复当成"已修复"就继续 V17**——若不强制 `--rerun-tasks` 复验、不人工核对报告存在，门禁仍可能因其他原因 SKIPPED。**证伪实验**：修复后必须 `--rerun-tasks` 并确认 HTML 报告文件存在，缺一不可；写入 CI 断言报告存在。
2. **覆盖修复后门禁变红，为赶进度下调阈值或排除大量类**——这是用门禁换取"绿色"的反模式。**证伪实验**：任何阈值下调须留审计记录与理由，禁止静默。
3. **解压测试因 Android 依赖复杂被无限期搁置**——若一直"待抽端口"，P1-04 永不落地。**证伪实验**：限定 2-3 天，先做能做的（UniversalExtractor 纯逻辑路径），抽端口作为后续项而非前置阻塞。
4. **git rewrite 历史导致协作者丢失提交或仓库损坏**——L3 操作未充分备份。**证伪实验**：先完整备份仓库 + 沟通 + 在克隆副本演练，再操作主仓库。
5. **CI 改成三模块后在国内网络/镜像下频繁失败，被回退到只跑 :app**——依赖拉取不稳定。**证伪实验**：先在本地完整跑三模块，确认依赖镜像可用，再改 CI。

**结论**：
- 可直接开始：T1（Jacoco）、T2（CI）、T3（密码外置）、T8（DI）、T9（文档）
- 应先实验再实施：T4（git rewrite）、T10（基准）
- 应降低优先级：P2-06 错误上报（需隐私评估）、P3 全项
- 当前不建议实施：V17 批量操作 UI 应在 T1/T5 修复后启动（避免在不可验证地基上扩张）
